CONTEXT
- `security_scan.py` is a single 3107-line, ~106KB file with zero external dependencies and no module/package boundaries — every function, class, constant, and data structure lives at module level, making the file both a monolith and the entire domain model.
- `find_all_files()` (line ~133) has an unreachable dead code path: two identical `return all_files, ext_map, name_map` statements at the end of the function; the second one is never reached.
- The scanner has **zero version control for dependencies** by design — it requires no `pip install`, no `requirements.txt`, no `pyproject.toml` — because the only runtime dependency is the external `pi` CLI on `$PATH`, making dependency pinning and reproducible builds infeasible.
- Cache invalidation uses a composite key (`scanner:rel_path:content_hash:prompt_hash:thinking`) hashed via MD5 to produce a 32-char hex filename — an MD5 collision is theoretically exploitable but practically irrelevant for the stated threat model; the more immediate concern is that changing any single component (content, prompt, or thinking level) invalidates the entire cache namespace for that scanner, so `--scan-thinking off → high` causes a full re-scan rather than a delta.
- The verify cache key additionally includes a `findings_signature` (MD5 of canonical JSON of the findings list), so if phase 2 changes the findings, the verify cache is automatically invalidated — this is the only cross-phase invalidation mechanism (scan → verify) and it works through the cache directory structure, not through any shared data structure.
- `call_pi()` writes the prompt to a temp file (`@file` syntax) to avoid ARG_MAX limits — the temp file is unlinked in a `finally` block, but if `os.unlink` raises `OSError` the cleanup silently fails; there's no fallback to a secure temp directory, so on a multi-user system the temp file lives in `/tmp/pi_prompt_*.txt` where other users can read the repo file content being scanned.
- The `extract_json_array()` function employs a six-layer recovery strategy (whole-response parse → fence strip → `raw_decode` from each `[` → truncated-array recovery via depth tracking → prose fallback → error dict) — while robust, it means the scanner **always attempts to parse model output as findings** rather than failing fast, which could mask a misconfigured or non-functional `pi` installation where the model returns gibberish but the recovery path silently produces an empty array or a truncated result.
- The same six-layer approach exists for objects in `extract_json_object()`, used for the discovery phase — both functions share no type annotations or return-type contracts, and the caller must always check `isinstance(parsed, (list, dict))` because the functions return `object | None`.
- Exit code semantics: exit 0 = clean (no findings at or above threshold), exit 1 = findings above threshold, exit 2 = at least one file errored/timed out — but `main()` at line ~3052 uses `sys.exit(2)` for errors while the documented behavior says exit 2 means "at least one file errored during scanning. It is *not* a finding, so the allowlist will not help" — CI integrations that only check `returncode != 0` cannot distinguish between "findings exist" and "scan was broken", making exit 2 effectively as "failing" as exit 1 for most CI systems.
- `EXCLUDE_FILES` hardcodes `"security_scan.py"` and `"sqli_scan.py"` — the scanner excludes itself from scanning, but there's no mechanism to exclude a custom `.security_scan/` directory from `EXCLUDE_FILES` (it's handled via `EXCLUDE_DIRS` instead, so `.security_scan` as a dir name works, but a differently-named state directory won't be excluded from scan results).
- `DEFAULT_MAX_FILE_SIZE` is 1 MiB and is checked during discovery; files exceeding it are silently dropped from all downstream phases — however, `verify_finding()` performs a defensive size re-check and skips oversized files with a stderr message, meaning a file that grows past 1 MiB between scan and verify will be silently skipped by the verifier rather than producing a finding.
- The `ProgressTracker` class uses a daemon thread for rendering — if `progress.stop()` is never called (e.g., due to an unhandled exception before the `finally` block in `main()`), the daemon thread will be forcibly terminated when the process exits, but the `try/finally` in `main()` does guarantee `progress.stop()` is called.
- The three-phase architecture (discovery → scan → verify) has independent tool flags per phase (`--discovery-tools`, `--scan-tools`, `--verify-tools`) with different defaults: discovery on, scan off, verify on — the different defaults reflect the different cost models (discovery is one call, scan is per-file, verify is per-file-with-findings) but means a user who enables scan-tools must also explicitly enable verify-tools to get the full picture.
- `results-tools/` and `results/` (and similarly `verifications-tools/` and `verifications/`) are parallel cache directories — a tools-mode scan writes to `results-tools/`, and the verify phase must read from the same directory (`scan_uses_tools` flag), but the report builder reads from whichever directory is selected by `phase_tools["scan"]` — if a user runs scan without tools but verify with tools, the report will look in `results/` for scan data and `verifications-tools/` for verify data.
- The allowlist matching uses `"first matching entry wins"` semantics with scanner wildcards (`"*"`), file wildcards (`"*"`), and line wildcards (`0`, `null`, or missing key matches the whole file) — this means a broad `"*"`/`"*"` entry at the top of the allowlist suppresses all findings for all scanners, and a more specific entry later is never reached.
- The `build_report()` function constructs the entire markdown report in memory as a `lines` list, then joins with `"\n"` and writes — for a repo with many files and findings this could be significant memory, but more critically, the function reads every cache JSON file in every scanner's results directory, meaning a corrupted or very large cache file could cause a crash or slow report generation with no partial output.
- `build_report()` and `build_csv_report()` share ~80% of their logic (loading results, applying allowlist, overlaying verification, computing severity/confidence counts) — the duplication means a change in one (e.g., a new severity level) must be replicated in both to maintain consistency.
- The verification phase uses `findings_signature()` to detect if the findings list has changed since the last verification, but the report builder's `load_verification_for_file()` also does this check — if the findings change between the scan phase and the report generation (e.g., during a concurrent run), the report will silently show stale verifications for the uncached files, because the report builder reads cached data without re-computing signatures.
- The CLI uses `argparse.BooleanOptionalAction` for the tool and progress flags — this creates both `--flag` and `--no-flag` options with a default; however, the default for `--progress` is `True` while `--no-progress` sets it to `False`, but the `enabled` parameter is passed as `bool(args.progress)` — since `--no-progress` sets the value to `False` and `--progress` to `True`, this is correct, but `enabled=False` creates a different ProgressTracker instance than `enabled=True` with `--no-progress`, which is a subtle distinction that doesn't affect behavior but makes the code harder to read.
- The `__pycache__/` directory is in `EXCLUDE_DIRS`, but Python bytecode (`*.pyc`, `*.pyo`) is not in `EXCLUDE_FILES`, so a Python bytecode cache sitting at the repo root (outside `__pycache__`) would be discovered and attempted to be scanned (though the binary check would likely catch it).
- `scan_file()` and `verify_finding()` both read the entire file content into memory for the prompt, plus compute a content hash via `content_hash()` which re-reads the file bytes — the same file is read twice (once for hash, once for content), and `verify_finding()` reads it a third time (to decode), though the file is typically already in the OS page cache.
- The `run_scanner()` function pre-computes `pending = [f for f in target_files if not _cache_usable(...)]` and then truncates with `pending[:max_files]` — the truncation happens **after** cache filtering, meaning if you have 100 files and `--max-files 10`, you get 10 files from the most recently modified (sorted by `str(Path)`) that need scanning, which may not be the files you want.
- `SEVERITY_ORDER` maps `"Critical": 4, "High": 3, "Medium": 2, "Low": 1` — but `confidence_counts_global` in the report uses `"Unverified": 0` and `"Unknown": 0`, meaning unverified and unknown findings have the same severity weight as "no finding" in the gated logic.
- The report's "Overall Risk" line uses emoji indicators (`🔴`, `🟠`, `🟡`, `🟢`, `⚠️`) for risk levels — these are UTF-8 emoji that may not render correctly in all terminals or CI log viewers, and could be stripped or garbled by log aggregation systems.
- The CSV/TSV report uses `csv.DictWriter` with `quoting=csv.QUOTE_MINIMAL` — this means fields containing commas, quotes, or newlines are quoted per RFC 4180, but the test at line ~1844 (`test_handles_newlines_and_quotes_in_fields`) confirms this works — however, if a finding's `explanation` or `fix` field contains a tab character, the TSV report will produce misaligned columns because the csv module doesn't handle the tab-vs-field separator distinction.
- `call_pi()` passes `--session-dir` to `pi`, meaning the LLM conversation context is persisted across calls for the same session directory — this is a security concern: if the session dir is shared across multiple runs, the model's conversation context from a previous scan (which may include sensitive code) could leak into a new scan session.
- The `session_dir` defaults to `.security_scan/sessions/` — if the user runs the scanner in a shared or public repo directory, the session files (which may contain full source code sent to the LLM) are stored in plaintext on disk.
- The `verify_prompt.txt` template sends the **entire file content** as `{file_content}` to the LLM for each file with findings — in a repo with many large files, this could mean megabytes of code sent to the model, and the prompt hash (used in cache keying) is computed on the template *before* `{file_content}` is substituted, so the cache key is the same regardless of file content, but the file content hash (`content_hash`) is the other dimension of the key.
- The `DEFAULT_DISCOVERY_PROMPT` and `DEFAULT_VERIFY_PROMPT` are embedded as raw Python strings in the source code — if a user edits the prompt files, the built-in defaults are silently used instead (via `load_discovery_prompt()` and `load_verify_prompt()`), which means a user can't easily see what fallback behavior they're getting without reading the source code.
- The scanner uses `shutil.move()` for atomic cache writes (write to `.tmp` then rename) — this only works atomically on the same filesystem, and if `.security_scan/` is on a different filesystem from `/tmp` (where `tempfile.NamedTemporaryFile` may place files), the `move` could fail with `OSError` and leave a partial cache entry.
- The `--formats` CLI option accepts extensions with or without leading dots — the `main()` function normalizes with `[e if e.startswith(".") else f".{e}" for ...]`, but this normalization only happens in `main()`, not in `find_all_files()` or the prompt templates, meaning a user who passes `--formats ".py,py"` would get duplicate `.py` entries in the scanner's extension list (handled by `dict.fromkeys()` dedup in `run_discovery()` but not elsewhere).
- The OWASP scanner registry (`OWASP_SCANNERS`) is a module-level dict with hardcoded scanner IDs (`B1`–`B10`) — adding a new scanner requires editing the source code directly (no config-file mechanism), and the `ALL_IDS` list is computed by parsing the `"B"` prefix and extracting the number, so a scanner with a non-numeric ID (e.g., `B11a`) would sort incorrectly.
