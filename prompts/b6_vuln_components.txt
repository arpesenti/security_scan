Analyze this source code file for **Vulnerable and Outdated Components** issues (OWASP B6:2025).

This scanner focuses on dependency management files and build configurations.

Look for:
- Dependencies with known critical vulnerabilities (log4j, jackson-databind, spring-framework, etc.)
- Use of deprecated, EOL, or unmaintained libraries
- Dependencies pinned to known-vulnerable versions
- Missing version pinning (floating versions that could pull in vulnerable updates)
- SNAPSHOT or development versions used in production builds
- Components from untrusted or non-official repositories
- Self-signed certificates in dependency chains
- Native libraries (JNI, .dll, .so) without integrity verification
- Components with known supply chain vulnerabilities
- Missing SBOM (Software Bill of Materials) generation in build process
- Insecure download URLs for dependencies (HTTP instead of HTTPS)
- Components that introduce unnecessary attack surface (large dependencies for simple tasks)
- Build scripts that execute remote code or download dependencies without verification
- Third-party components with debug/logging modes enabled

1. Line number(s)
2. The vulnerable code snippet
3. Severity (Critical/High/Medium/Low)
4. Brief explanation of the vulnerability
5. Suggested fix
6. The taint path as two fields: "source" (where untrusted input enters —
   request param, argv, socket read, queue message, env var, file upload...) and
   "sink" (where it becomes dangerous — SQL execute, shell exec, deserialization,
   HTML output, HTTP request...). Both fields are REQUIRED strings; if you
   cannot name a concrete source, the finding must not be emitted.

Do NOT flag these safe patterns (negative evidence — a finding without a
concrete source/sink taint path is worse than a missed one):
- Parameterized queries, prepared statements, and ORM/query-builder calls
- Logging of constant or internal strings (no untrusted data in the format)
- Values that never cross a trust boundary (hardcoded config, internal
  constants, values that stay inside a single trusted module)
- Test fixtures and test-only code paths
- Defense-in-depth wrappers that already validate/escape their inputs
